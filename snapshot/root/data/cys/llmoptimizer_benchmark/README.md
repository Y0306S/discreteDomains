# LLMOptimizer Benchmark Data and HPO Examples

This repository contains the code and example scripts for reproducing or consuming benchmark HPO traces.

The main contents are:

- `datasets_bundle/`: classification and regression datasets used by the benchmark. This directory is provided separately via cloud drive.
- `history_data/`: historical HPO trajectories collected on these datasets. This directory is provided separately via cloud drive.
- `examples/benchmark/`: example scripts for generating HPO history and evaluating a single hyperparameter configuration.

## Environment

Python 3.8 is recommended.

```bash
pip install -r requirements.txt
```

## Datasets

After downloading and extracting `datasets_bundle.zip`, place `datasets_bundle/` in the project root:

```text
datasets_bundle/
  cls_datasets/          # 71 classification datasets, CSV format
  rgs_datasets/          # 33 regression datasets, CSV format
  dataset_info/
    classification.csv   # metadata for classification datasets
    regression.csv       # metadata for regression datasets
```

The helper function `get_dataset_info(task_type, dataset)` in `examples/benchmark/benchmark_utils.py` resolves the CSV path for a given task type and dataset name.

Current conventions:

- `task_type="cls"` reads from `datasets_bundle/cls_datasets/`.
- `task_type="rgs"` reads from `datasets_bundle/rgs_datasets/`.
- The label/target column is the last column by default.

Dataset metadata is stored in `datasets_bundle/dataset_info/`.

- `classification.csv`: metadata for classification datasets.
- `regression.csv`: metadata for regression datasets.
- `n`: number of rows, i.e. number of samples.
- `p`: number of columns/features.
- `C`: number of classes for classification tasks.

## History Data

After downloading and extracting `history_data.zip`, place `history_data/` in the project root:

```text
history_data/
  cls/
    bal_acc/
      ada/
        lightgbm.json
        random_forest.json
        ...
  rgs/
    mse/
      abalone/
        lightgbm.json
        random_forest.json
        ...
```

Each JSON file represents one HPO trajectory for:

```text
task type / metric / dataset / algorithm
```

For example:

```text
history_data/cls/bal_acc/ada/lightgbm.json
```

is the OpenBox History generated by tuning `lightgbm` on the classification dataset `ada` using `bal_acc` as the metric.

The most important field in each history JSON is `observations`. Each observation is one evaluated hyperparameter configuration:

- `config`: the algorithm and hyperparameters evaluated in this trial.
- `objectives`: the OpenBox objective value.
- `trial_state`: trial status. `0` means success.
- `elapsed_time`: evaluation time for this trial.
- `create_time`: timestamp when this trial was created.

Important: `objectives` follows the OpenBox minimization convention, so smaller is better.

For classification metrics such as `bal_acc`, the actual metric is larger-is-better, so Mindware stores the negative score as the OpenBox objective. For regression metrics such as `mse`, the metric itself is smaller-is-better, so the objective is usually a positive MSE value.

## Generate HPO History

Example script:

```text
examples/benchmark/run_hpo_history_example.py
```

This script runs HPO and saves an OpenBox History JSON compatible with the files under `history_data/`.

Example:

```bash
python examples/benchmark/run_hpo_history_example.py \
  --task_type cls \
  --dataset ada \
  --algorithm lightgbm \
  --metric bal_acc \
  --epoch 30 \
  --history_dir ./history_data \
  --output_dir ./benchmark_data/hpo_example
```

This example:

- Loads `datasets_bundle/cls_datasets/ada.csv`.
- Splits out an external test set with `test_size=0.2`.
- Uses a holdout validation split inside the training data for HPO.
- Tunes the hyperparameters of `lightgbm`.
- Saves the HPO trajectory to:

```text
history_data/cls/bal_acc/ada/lightgbm.json
```

Internally, the script uses single-algorithm CASH:

```python
CASH(include_algorithms=[algorithm], optimizer="smac")
```

Since only one algorithm is included, this is equivalent to HPO for that algorithm. The optimizer is SMAC/OpenBox-style Bayesian Optimization. It repeatedly proposes hyperparameter configurations from the search space, evaluates them on the validation split, and records the resulting observations into an OpenBox History.

You can also run all built-in algorithms for a dataset:

```bash
python examples/benchmark/run_hpo_history_example.py \
  --task_type cls \
  --dataset ada \
  --algorithm all \
  --epoch 30
```

Supported algorithms in the example:

```text
adaboost
catboost
extra_trees
gradient_boosting
k_nearest_neighbors
lightgbm
random_forest
xgboost
```

## Search Space and Config Evaluation

Example script:

```text
examples/benchmark/evaluate_config_example.py
```

This script demonstrates two interfaces:

1. How to obtain the HPO search space for a given algorithm on a given dataset.
2. How to evaluate a provided hyperparameter configuration on the validation split.

The script has no command-line arguments. Edit the variables at the top of the file:

```python
TASK_TYPE = "cls"
DATASET = "ada"
ALGORITHM = "lightgbm"
HYPERPARAMETERS = {
    "learning_rate": 0.05,
    "num_leaves": 64,
    "n_estimators": 200,
}
```

Run:

```bash
python examples/benchmark/evaluate_config_example.py
```

### 1. Get The Search Space

Core code:

```python
cs = get_hpo_cs(
    estimator_id=ALGORITHM,
    task_type=task_type_id,
    **get_cs_args(
        resampling_params={"test_size": VALID_SIZE, "shuffle": False},
        data_node=train_node,
    ),
)

print(cs)
```

`cs` is a `ConfigSpace.ConfigurationSpace` object. It contains the tunable hyperparameters, ranges, default values, and constraints for the selected algorithm.

For example, `lightgbm` prints entries like:

```text
lightgbm:learning_rate, Type: UniformFloat, Range: [0.001, 0.3], Default: 0.1, on log-scale
lightgbm:n_estimators, Type: UniformInteger, Range: [100, 1000], Default: 500, Q: 50
lightgbm:num_leaves, Type: UniformInteger, Range: [31, 2047], Default: 128
```

### 2. Evaluate A Hyperparameter Configuration

The script first starts from the default configuration in the search space, then overrides the fields given in `HYPERPARAMETERS`:

```python
config_dict = cs.get_default_configuration().get_dictionary()
config_dict["algorithm"] = ALGORITHM

for name, value in HYPERPARAMETERS.items():
    full_name = name if ":" in name else f"{ALGORITHM}:{name}"
    config_dict[full_name] = value

config = Configuration(cs, values=config_dict)
```

Then it calls the evaluator:

```python
result = evaluator(config, save=False)
```

The returned `result` follows the OpenBox format. The main value is:

```python
result["objectives"][0]
```

This is a minimization objective, so smaller is better.

The script prints a JSON summary like:

```json
{
  "task_type": "cls",
  "dataset": "ada",
  "algorithm": "lightgbm",
  "metric": "bal_acc",
  "objective": -0.7722647498132935,
  "objective_direction": "minimize",
  "config": {
    "algorithm": "lightgbm",
    "lightgbm:learning_rate": 0.05,
    "lightgbm:n_estimators": 200,
    "lightgbm:num_leaves": 64
  }
}
```

Here `objective_direction="minimize"` means smaller is better. For larger-is-better metrics such as `bal_acc`, Mindware returns the negative score as the OpenBox objective.
