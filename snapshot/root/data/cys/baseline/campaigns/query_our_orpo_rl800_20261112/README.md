# Query ORPO and GRPO training

Source: `query_train800_author_fixed_20261004`, seed0 LOLBO histories, frozen train800/test200 split. No held-out measurements enter training. Export canonicalizes the actual executed join tree from `extra_info.plan`; latent vectors and repaired raw proposals are not supervision. Independent audit checks strict aliases/operators, source trees and runtimes, chronological prompt boundaries, and BOLT per-task top-ten ranking.

- ORPO: 817 causal preference pairs from 336 of the 800 scanned queries. Chosen plan improves the frozen prefix incumbent; rejected plan is measured, uncensored, unseen in that prefix and does not improve. Rejection selection uses the ML 50/50 Pareto rule on integer-plan edit similarity and normalized runtime gap. Clean Qwen3.5-9B, rank32/alpha64 LoRA, one epoch, LR1e-5, effective batch8, 103 optimizer steps. Assistant-only token labels checked through actual LLaMA-Factory preprocessing, zero truncation (max13,161 tokens).
- GRPO: 32 queries selected among 187 still improving in rounds80–100, using ML Pareto-front/mean-percentile ordering on late improvement counts and percentages, balanced by SQL template and join count. Selection spans 14 templates and joins6–15. Four phases: retrieval3/5/10, normal20/30/40, normal50/70/90, normal60/80/100; 384 context groups. All measured initialization rows plus the completed acquisition rounds form each causal prefix. Prompts retain actual top/bottom5 and recent up-to50 distinct uncensored plans. Retrieval has real SQL/alias differences and exact source-GP agreement; SQL appears once per task rather than repeated in each comparison. All384 prompts fit without truncation (max14,638 plus <=1,024 generation tokens).
- GRPO samples at least4 and at most10 with an identical frozen prompt until a strict measured improvement; exactly4 training members follow ML's deterministic random replacement rule. No random fallback. Duplicate outputs are retained for anchored rejection loss. The frozen reference is the exact new ORPO adapter, and policy/optimizer state continue across phases with two passes each.
- Real PostgreSQL training evaluation uses dedicated IMDb instances on ports20580/20581, three CPU cores each and up to two PostgreSQL parallel workers. Bound = max(1second, min(120seconds, 2×prefix incumbent runtime)). Timeout bounds receive fixed reward−0.5, no invented measured loss or delta-best. This screens slow plans while preserving the chance to finish improvements below the incumbent. Every measured attempt/result is durable; an unresolved interruption is held for audit rather than silently replayed.

GPU0 is reserved for sequential ORPO then GRPO, with a48GiB allocation cap. The durable queue only launches RL after the data, source GP, retrieval, token, oracle and exact-parent gradient checks pass. Infrastructure errors stop the dependent phase and are reported in `services/queue_status.json`; a monitor does not auto-restart uncertain oracle work. Completed RL releases its two PostgreSQL instances and CPU reservation.
