# Peptide evaluation design: BOLT-generated initializations

Draft prepared 2026-11-12, updated after user clarification: the warm-start model generates the starting pool and the ORPO+RL model takes over, following the ML workflow. This document designs that pipeline; it does not start generation or arm a production queue.

## Scope and model identity

Use the same fixed 200 held-out peptide tasks, excluding the 800 training tasks. Each target gets exactly 50 distinct, feasible peptides generated by the BOLT warm-start language model, then measured with the existing APEX bacteria_0 oracle. This is 10,000 accepted and scored initializations in total. The existing verified mutation pool has 100 initializations/task; it is a different source and will not be relabeled as BOLT model output.

Proposed BOLT generator: the just-completed full warm-start checkpoint at `/root/data/cys/baseline/campaigns/peptide_warmstart_full800_20261111/model/checkpoint-1500` (3 epochs, 1,500 updates). Pin the final weight shards, tokenizer and chat-template hashes before launch. This checkpoint choice is proposed explicitly; the older October BOLT training artifact is a different checkpoint.

Confirmed pipeline: the full three-epoch warm-start model generates initialization, then the final peptide ORPO+RL adapter (`cycles/round1`) under `/root/data/cys/baseline/campaigns/peptide_our_orpo_rl800_20261111` drives our-method optimization with FSBO. Its adapter SHA is `ae51047dc74b9da4ef71913ea3ba31f354f270f5c0204db5a309e314d645b474`. The warm-start is a full model with different base weights; ORPO+RL must be loaded on its original Qwen3.5-9B base, not on the warm-start weights. Transfer the measured initializations between stages, not weights or KV tensors. Separate ORPO-only and warm-start-only optimization arms are outside this proposed run.

## Generating and freezing the shared pool

1. Reuse the BOLT SFT prompt builder from `tools/bolt_peptide_sft.py`: the reference, objective and exact task constraints, with no target scores or observed target examples. Use the training-compatible chat template and one JSON sequence per response. Freeze this prompt for all samples of the same task.
2. Sample stochastically using distinct, persisted per-task RNG states/seeds. Proposed starting sampling parameters are temperature 1.0, top_p 0.9, top_k 50 and 128 maximum output tokens; confirm them in the evaluation recipe before generation. Do not request a 50-entry JSON batch from a model trained to emit one sequence.
3. Accept the first 50 valid unique sequences in generation order. Validate alphabet ACDEFGHIKLMNPQRSTVWY, length 1–30, at most one C, and similarity `1 - Levenshtein(candidate, reference)/len(reference) >= 0.75`. Exclude the unchanged reference, matching the existing mutation-pool convention. Reject invalid JSON, infeasible peptides and repeats locally, recording every attempt and its reason. Do not edit or repair outputs, select the best 50 by MIC, or silently substitute random peptides. A bounded generation-attempt limit and underfilled-task policy must be set before launch; report an underfilled pool rather than claim success.
4. Score accepted sequences with the pinned APEX bacteria_0 oracle. Batch CPU scoring where supported, with validated score-to-sequence alignment. Store MIC as the minimization objective and negative MIC only where the optimizer expects maximization. Generated text never supplies its own measured score.
5. Freeze one manifest for all selected arms, containing task/reference, checkpoint identity, exact prompt/token digest, RNG state/seed, attempt index, sequence, similarity, APEX version/hash, MIC and measurement timing. Share exactly the same 50 sequences, scores and order across arms. Count the 50 as imported initialization, separately from subsequent optimization attempts and fresh oracle evaluations.

## KV-cache behavior

The major immediate cache opportunity is the 50 independent BOLT samples for a task: they all use the identical frozen prompt and checkpoint. Pin each task to one replica. Prefill once, keep an immutable prompt snapshot, and clone it before every sample so generated tokens do not contaminate later samples. The current SemanticOPT exact-prompt cache already follows this cloning pattern.

BOLT SFT examples are short (196–219 tokens including the answer in the training audit). The current cache defaults to skipping prompts shorter than 256 tokens. Measure actual generation-prompt lengths and expose/configure an appropriate minimum (proposed 128 tokens); otherwise these samples may receive no cache reuse at all. Keep retained cache memory bounded, evict under pressure, and preserve the same request RNG when an optional-cache allocation fails.

Sharing initial sequences does not permit sharing KV tensors across the BOLT, ORPO and ORPO+RL checkpoints, across different peptide references, or across changed prompt text. Clear/isolate caches by complete checkpoint and prompt identity. During optimization, best/worst examples, Recent50 and other measured feedback change the prompt. The existing cache matches the complete prompt, so its reliable hits are repeated samples/retries from an unchanged context. It does not yet cache an arbitrary common prefix across turns. Keep the existing training-compatible optimization prompt format for the first implementation. Any later static-prefix cache needs an explicit prefix-snapshot implementation and separate validation for Qwen3.5's recurrent as well as attention state; a static block in the prompt alone is insufficient.

## ORPO+RL with FSBO optimization

Initialize each arm from the frozen 50 measurements and use its appropriate trained prompt and optimizer integration. Preserve current-task rules, real top/bottom examples and Recent50. The current peptide RL model uses retrieval at its early retrieval turns and normal prompts at former explore/exploit turns, without Good/Bad Region summaries; do not restore a different phase policy silently. Retrieval comes only from train800 and must describe source/target differences.

Keep arm seeds, initial pool, APEX oracle and optimization budget aligned. Proposed budget: 80 optimization attempts per task, following the current ML ORPO+RL+FSBO evaluation, with the original 100-attempt arm-selection schedule retained as in ML. One measured selected candidate per successful attempt; parse/constraint/duplicate retries are recorded, and optimizer-level failed attempts count under the ML accounting policy. Reuse ML hybrid arm-selection/retry behavior (`HPUCB_fsbo_p07p03_retry5_llm8_cool20`), mapped to the validated peptide FSBO latent model, APEX objective and trained peptide prompts. Preserve the peptide RL early retrieval/later normal prompt override. The transfer of optimizer schedule and retry semantics needs an explicit integration test. This is 16,000 optimization attempts across 200 tasks, plus 10,000 measured initializations. The 80-attempt limit is a design proposal, not an applied budget change. Comparing against older random-initialized runs must identify the changed initialization condition; an apples-to-apples method comparison uses the same new BOLT pool for every included arm.

Report initial best MIC and improvement from that baseline, best-so-far curves versus new oracle evaluations, area under those curves, feasibility/duplicate rates, fallback provenance if any is explicitly enabled, and paired task-level differences between arms. Report initialization-generation cost separately and also include it in end-to-end time. No model-weight updates occur during held-out evaluation.

## Execution order and runtime estimate

The production handoff should require SemanticOPT query's audited completion marker AND all 200 tasks at the full effective query budget (40,000 total evaluations), not just a process exit or a stale status file. Then drain requests and release only that campaign's inference replicas/tunnel before loading the peptide generator. Other workloads remain owned by their own controllers.

Order: query completion -> BOLT initialization generation/scoring -> frozen-pool audit -> selected peptide evaluation arms. Use an isolated campaign with task claims, checkpoint/model/pool hashes, durable RNG and request/measurement journals. Resume committed records without repeating APEX calls; unresolved oracle calls require inspection. Do not publish a completed task with fewer than 50 initializations or an unfinished optimization budget.

First validate generation, parsing, constraints, duplicate rejection, task/cache isolation, checkpoint identity, deterministic replay, and cached-vs-uncached inference behavior on small train-task smoke tests. Then measure a small set of production tasks as part of the same preserved pool. Record prompt prefill, decoding, cache reuse/memory, valid unique acceptance rate, APEX time and total wall time.

If acceptance is p and generation takes g seconds/request across R effective replicas, the initialization generation workload is approximately `10000*g/(p*R)` seconds, plus scoring and overhead. Use measured committed throughput to validate this component estimate. The full optimization ETA additionally requires the agreed rounds/budget and an actual pilot of the selected method; query-plan timings do not predict peptide runtime.

## Proposed recipe to review

- Generator: completed full warm-start at checkpoint 1500 (3 epochs).
- Initial pool: first 50 feasible unique warm-start samples/task, measured and frozen.
- Optimizer: final ORPO+RL adapter + peptide FSBO, for all 200 held-out tasks.
- Budget: 80 optimization attempts/task proposed to match current ML; retain the ML original 100-attempt selection schedule.
- Sampling: temperature 1.0, top_p 0.9, top_k 50, one sequence/response, 128 output tokens.
- Initialization bound: propose 500 samples/task maximum; underfilled tasks report incomplete and do not receive silent random replacement.
- Order: wait for fully audited SemanticOPT query completion, then generate/score/freeze initialization, then optimize.
- Run a short operational pilot to measure unique acceptance, inference, oracle and FSBO overhead before giving a peptide completion estimate.

Implementation and production queue remain pending review of this proposed recipe.
